# نظام إدارة الفنادق — فندق النخبة

نظام سحابي لإدارة الفنادق والشقق المخدومة، بواجهة عربية (RTL) مصممة لسرعة العمل في
الاستقبال. يُبنى المشروع على مراحل، ولا تبدأ أي مرحلة قبل اجتياز اختبار قبول سابقتها.

> **الحالة:** المراحل 1 (الأساس) و 2 (قاعدة البيانات) و 3 (بيانات العرض) و 4 (لوحة المعلومات) — مكتملة.

## التشغيل محليًا

```bash
npm install
cp .env.example .env
# ولّد مفتاح التوقيع وضعه في AUTH_SECRET

npm run dev      # بيئة التطوير على http://localhost:3000
npm run build    # بناء الإنتاج
npm run start    # تشغيل نسخة الإنتاج
```

## النشر على هوستنجر (Node.js — Deploy from GitHub)

1. في لوحة hPanel افتح **Node.js** واربط المستودع على الفرع `main`.
2. اضبط الإعدادات:
   - **Node version:** 20 أو أحدث
   - **Build command:** `npm ci && npm run build`
   - **Start command:** `npm run start`
   - **Application root:** جذر المستودع
3. أضف متغيرات البيئة — `AUTH_SECRET` و `DATABASE_URL` إجباريان.
4. كل دفعة (push) إلى `main` تُطلق إعادة بناء ونشر تلقائيًا.

### إنشاء قاعدة البيانات على هوستنجر

hPanel → Databases → MySQL Databases، وثلاث خطوات لا اثنتان:

1. **Create Database** — الاسم يبدأ ببادئة الحساب، مثل `u123456789_hotel`
2. **Create User** — بنفس البادئة
3. **اربط المستخدم بالقاعدة** — قسم منفصل أسفل الصفحة، امنحه **ALL PRIVILEGES**

الخطوة الثالثة هي التي تُنسى، وخصوصًا لمن اعتاد Supabase أو أي قاعدة مُدارة
تربط الاثنين تلقائيًا. بدونها ينجح الدخول ويفشل كل استعلام بالخطأ **1044**،
ورسالته تبدو كأنها مشكلة كلمة مرور فترسلك إلى المكان الخطأ.

للتأكد: افتح **phpMyAdmin** — إن ظهرت القاعدة في القائمة اليسرى فالربط تمّ.

ثم ركّب الرابط:

```
mysql://المستخدم:كلمة_المرور@localhost:3306/اسم_القاعدة
```

- **المضيف `localhost`** لأن القاعدة على نفس خادم التطبيق. لا تستخدم مضيفًا
  خارجيًا: اللوحة تُصدر عشرات الاستعلامات لكل عرض، ورحلة شبكة لكل واحد تحوّل
  زمن الفتح من مللي ثانية إلى ثوانٍ.
- **البادئة واحدة** للمستخدم والقاعدة. رقم مختلف بينهما = الخطأ 1044.
- **رمّز الرموز في كلمة المرور.** أخطرها `#`: في أي رابط يبدأ الجزء المرجعي،
  فيُقتطع كل ما بعده وتصل كلمة المرور ناقصة — أو يفشل التحليل كليًا.

  | `#` ← `%23` | `&` ← `%26` | `@` ← `%40` | `%` ← `%25` |
  |---|---|---|---|
  | `/` ← `%2F` | `?` ← `%3F` | `:` ← `%3A` | مسافة ← `%20` |

  في لوحة الاستضافة تُدخل كلمة المرور **أصلية بلا ترميز**؛ الترميز يخص الرابط
  وحده. الأبسط أن تتجنّب الرموز أصلًا: عشرون حرفًا وأرقامًا أقوى من عشرة برموز،
  وبلا احتمال خطأ في الترميز.

عند أي فشل، `npm run db:check` على الخادم يقول السبب بالضبط.

### تهيئة قاعدة البيانات (مرة واحدة)

بعد أول نشر، شغّل من طرفية هوستنجر داخل مجلد التطبيق:

```bash
npm run db:check    # تشخيص الاتصال — شغّله أولًا إن فشل أي شيء
npm run db:deploy   # تطبيق الـ migrations
npm run db:seed     # الصلاحيات والأدوار وحساب مدير أولي
```

`db:check` يقرأ `DATABASE_URL` ويحاول الاتصال ويقول السبب الدقيق عند الفشل:
كلمة مرور خاطئة، أو مستخدم غير مُسنَد للقاعدة، أو مضيف غير صحيح، أو رموز غير
مرمّزة في كلمة المرور. يعمل على الخادم لا عبر رابط عام — نقطة `/api/health`
تقول «متصل» أو «غير متصل» فقط عمدًا، لأن رابطًا عامًا يشرح سبب رفض القاعدة
يخبر الغرباء عن بنيتك.

`db:deploy` آمن للتكرار: يطبّق الـ migrations غير المطبّقة فقط ولا يمسح بيانات.
و`db:seed` آمن للتكرار كذلك — لا يعيد تعيين كلمة مرور غُيّرت لاحقًا.

### بيانات العرض (بيئة العرض فقط)

```bash
npm run db:demo-seed      # فندق أروقة جدة كاملًا — 40 غرفة، 491 حجزًا
npm run db:demo-validate  # يتحقق أن كل رقم يطابق سجلاته
npm run db:demo-reset     # يمسح بيانات العرض فقط
```

**لا تشغّل `db:demo-seed` على تثبيت حقيقي.** بذرة النظام (`db:seed`) تُنشئ ما
يحتاجه أي تثبيت إنتاجي فقط: الصلاحيات والأدوار وحساب مدير واحد للإقلاع. بذرة
العرض تُنشئ فندقًا كاملًا وتمسح بياناته التشغيلية عند كل تشغيل.

`db:demo-reset` يرفض العمل إذا كان `NODE_ENV=production` ما لم تضبط
`ALLOW_DEMO_RESET=true` صراحةً، ولا يمسّ إلا المنشأة الحاملة لعلامة العرض في
إعداداتها — فندق حقيقي في نفس القاعدة لا يتأثر.

التطبيق يستمع على `process.env.PORT`، وهو ما يمرره هوستنجر، فلا حاجة لتعديل إضافي.

### ⚠️ لا تضف `NODE_ENV=production` كمتغير بيئة

`next start` يضبطها بنفسه. أما أثناء التثبيت فإن `NODE_ENV=production` تجعل npm
يتخطى `devDependencies` بالكامل — وهذا يكسر البناء.

المشروع محصَّن ضد هذه الحالة: كل حزم وقت البناء (`tailwindcss`, `postcss`,
`autoprefixer`, `typescript`, `@types/*`) موجودة في `dependencies` لا في
`devDependencies`، فينجح البناء حتى مع `npm ci --omit=dev`. لكن الأفضل ألا تضبط
المتغير أصلًا.

**سبب هذا القرار:** بدون `typescript` لا يقرأ Next ملف `tsconfig.json`، فتتوقف
مسارات `@/*` عن العمل وتظهر أخطاء `Module not found` لملفات موجودة فعلًا. وبدون
`tailwindcss` تفشل معالجة CSS. الأعراض تبدو وكأن الملفات ناقصة، والسبب الحقيقي
طريقة التثبيت.

### الفحص قبل كل دفعة

```bash
npm run verify    # typecheck + lint + build
```

الـ lint معطّل أثناء بناء الإنتاج (`eslint.ignoreDuringBuilds`) لأن أدوات الفحص
تبقى في `devDependencies` التي قد لا تُثبَّت على الخادم. الفحص مسؤولية `npm run verify`
محليًا قبل الدفع.

## نموذج الصلاحيات

الصلاحية هي وحدة التفويض في كل مكان: التنقل، وحماية الصفحات، ومسارات الـ API.
الأدوار مجرد حزم من الصلاحيات — **لا يُفحص الدور مباشرة في كود الميزات، بل الصلاحية**.

```
الطلب → middleware (هل توجد جلسة صالحة؟)
      → requirePermission (هل تملك الجلسة هذه الصلاحية؟)
      → الصفحة
```

إخفاء الأزرار في الواجهة تحسينٌ لتجربة المستخدم، وليس وسيلة الحماية. المنع الحقيقي
يقع على الخادم قبل إرسال أي محتوى.

| مدير الفندق | 15 |
| موظف استقبال | 10 |
| محاسب | 11 |
